## Step 1: Write Your First YAML Manifest

Create a file: `~/Documents/LearnK8s/manifests/nginx-deployment.yaml`

Apply it:

```bash
$ kubectl apply -f manifests/nginx-deployment.yaml
$ kubectl get deployments
$ kubectl get pods --show-labels
```

## Step 2: Add a Service Manifest

A service provides a stable IP address, DNS name (nginx-service), and traffic routing to the pods.

Create: `~/Documents/LearnK8s/manifests/nginx-service.yaml`

```bash
$ kubectl apply -f manifests/nginx-service.yaml
$ minikube service nginx-service --url
```

## Step 3: Work with Namespaces

```bash
$ kubectl create namespace dev
$ kubectl create namespace staging
$ kubectl get namespace
```

Deploy into a specific namespace:

```bash
$ kubectl apply -f manifests/nginx-deployment.yaml -n dev
$ kubectl get pods -n dev
```

These 2 separate Deployments with the same name `nginx-app` in the `dev` namespace are completely independent from those in the `default` namespace — deleting one doesn't affect the other.

Namespaces are like separate environments — think of them as:

- `default` = production
- `dev` = development
- `staging` = staging

**Tip:** Use `-A` (--all-namespaces) to see everything:

```bash
$ kubectl get pods -A
```

## Step 4: ConfigMaps & Secrets

### ConfigMap (Non-sensitive Config)

Stores non-sensitive configuration that pods can read at runtime (instead of hardcoding in your app).

Example usages: database host, API endpoints, feature flags, log levels.

#### Approach A: Imperative (quick for testing)

```bash
$ kubectl create configmap app-config --from-literal=ENV=development --from-literal=LOG_LEVEL=debug
$ kubectl describe configmap app-config
$ kubectl get configmap app-config -o yaml
```

#### Approach B: Declarative (best practice for production)

Create: `~/Documents/LearnK8s/manifests/app-config.yaml`

```bash
$ kubectl apply -f manifests/app-config.yaml
$ kubectl describe configmap app-config
```

Your app code just reads standard environment variables — it doesn't need to know about Kubernetes or ConfigMaps. Kubernetes handles the injection.

### Secret (Sensitive Data, Base64-Encoded)

Stores passwords, API tokens, certificates.

Now let's see how we can create a Secret called `db-creds` with username and password.

#### Approach A: Imperative (quick for testing)

```bash
$ kubectl create secret generic db-creds --from-literal=username=admin --from-literal=password=supersecret
$ kubectl get secret db-creds -o yaml    # Notice values are base64-encoded
$ kubectl get secret db-creds -o jsonpath='{.data.password}' | base64 --decode  # Decode to see plain text
```

#### Approach B: Declarative (best practice)

Create: `~/Documents/LearnK8s/manifests/db-secret.yaml`

```bash
$ kubectl apply -f manifests/db-secret.yaml
$ kubectl get secret db-creds -o yaml
```

### Secret Types

The default type is "Opaque" which stores arbitrary user-defined data (passwords, API keys, etc). Other common Secret types include:

| Type                                  | Use Case                    | Example                     |
| ------------------------------------- | --------------------------- | --------------------------- |
| `Opaque` (default)                    | Custom app secrets          | passwords, API keys, tokens |
| `kubernetes.io/dockerconfigjson`      | Docker registry credentials | Pull private Docker images  |
| `kubernetes.io/tls`                   | SSL/TLS certificates        | HTTPS, Ingress certificates |
| `kubernetes.io/basic-auth`            | HTTP basic authentication   | API credentials             |
| `kubernetes.io/ssh-auth`              | SSH private keys            | Git SSH keys, SSH access    |
| `kubernetes.io/service-account-token` | Pod-to-API authentication   | Auto-generated by K8s       |

In 99% of cases, use `type: Opaque` for your custom secrets. Use specific types only when integrating with Kubernetes features (e.g., `tls` for Ingress, `dockerconfigjson` for registries).

**Note:** In practice, different namespaces (dev/staging/prod) have different ConfigMaps/Secrets. You can change config without rebuilding containers. For deeper dive with usage examples, see: [L2_ConfigMaps_and_Secrets_Deep_Dive.md](L2_ConfigMaps_and_Secrets_Deep_Dive.md).

## Step 5: Useful kubectl Commands to Practice

```bash
$ kubectl logs <pod-name>              # View container logs
$ kubectl exec -it <pod-name> -- bash  # Shell into a running container
$ kubectl port-forward <pod-name> 8080:80  # Forward local port to pod
$ kubectl get events                   # Cluster events (great for debugging)
$ kubectl explain deployment.spec      # Built-in docs for any field
```
